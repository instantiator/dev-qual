# Plan: quality and reliability enhancements

This is the plan requested by `001.1 - quality and reliability enhancements.md`. It restructures this repository from 13 flat markdown files into a tiered, script-backed guidance system that can be installed into any project and used by any coding agent — including small-context, weaker-reasoning models — to deliver features, bug-fixes, and improvements to a consistently high standard.

## Guiding principles

1. **Scripts over prose** — every deterministic checklist becomes a script that prints an actionable PASS/FAIL report. Deterministic work moves out of the model.
2. **Enforcement over memory** — git hooks are the universal backstop that no model can forget; agent-platform hooks are optional accelerators.
3. **Hard size budgets** — one topic per file, imperative rules, frontmatter descriptions used for routing. Small models read one short doc at a time.
4. **One source of truth, thin adapters** — skills and docs are plain markdown playbooks; per-platform wiring (Claude Code, OpenCode) is generated from them, never duplicated.

The design bet: even if a small model ignores every written instruction, the pre-commit hook forces it to confront failures at commit time with actionable fix-hints. "FAIL lint — run `npm run lint -- --fix`" is a loop weak models handle well; a 48-line checklist held in memory is not.

## 2. Doc format convention (OKF-lite)

A pragmatic subset of the [Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing): markdown + YAML frontmatter + an `index.md` per directory + cross-links. Full OKF adds ceremony (timestamps, rigid typing) with little payoff here — git owns history.

**Frontmatter, required on every doc:**

```yaml
---
type: standard | process | skill | index | reference
title: TypeScript standards
description: Rules for TypeScript code — strict mode, comments, tooling. Read when writing or reviewing .ts files.
tags: [typescript, language]
---
```

The `description` field is load-bearing: it is the **routing text**. Index files list children with their descriptions, and `scripts/lint-docs.sh` verifies they stay in sync. A description must say *when to read the doc*, in one or two sentences.

**Size budgets, enforced by `lint-docs.sh`:**

| Doc type | Budget |
|---|---|
| agents-files entry | ≤ 30 lines |
| index.md | ≤ 40 lines |
| standard (language/framework/infra/ci) | ≤ 60 lines |
| process doc | ≤ 80 lines |
| SKILL.md | ≤ 100 lines |

**Style rules:** one topic per file; imperative bullet rules ("Use strict mode", never "It is recommended that…"); each rule may carry a one-line *why* in parentheses; relative links only; GFM tables and mermaid welcome, but budgets still apply.

## 3. Skills

Each skill is a directory with a `SKILL.md` (frontmatter: `name`, `description` = when-to-use trigger text, `tags`) plus optional `scripts/`. The body follows a fixed structure: **When to use → Questions to ask → Steps → Scripts → Validate**. This is directly compatible with Claude Code's skill format and readable as a plain playbook by anything else.

The brief's 14 skill items consolidate into 11 skills:

| Skill | Trigger / when used | Interactive questions | Backing scripts | Validation |
|---|---|---|---|---|
| `project-setup` | New project, empty repo, "scaffold X" | Language/framework? Templating tool (create-nest-app, dotnet new, vite) or manual? Test tiers? Docker? | `check-prereqs.sh`; templating CLIs | `check.sh` passes on the fresh project; README + docs/index.md exist |
| `ci-setup` | "Set up CI", repo without workflows | Platform (GH Actions/GitLab/gitea)? Which check.sh stages in CI? Deploy from CI? | actionlint / platform validators via skill script | Workflow yaml validates; first pipeline green |
| `testing-setup` | "Add tests", missing test suite tier | Which tiers (unit/integration/e2e/browser/api)? Framework? Test data strategy? | Generates `scripts/run-<suite>-tests.sh` in the project from templates | Each generated script runs and exits 0 on a sample suite |
| `quality-review` | After coding, "review this", check.sh failures | Scope: diff only or adjacent code too? Fix or report? | `check.sh`, `npx aislop scan` | check.sh PASS; aislop clean; comments match intent (listed manual step) |
| `docs-review` | Docs stale, post-feature, "update docs" | Which docs relate to changed code? Diagrams needed? | `lint-docs.sh` (link/format checks) | No dead links; docs describe actual behaviour (agent cross-checks code) |
| `deploy` | "Deploy", "run it locally", release tasks | Local or remote? Environment? First time or repeat? | Project's start/compose scripts; skill wraps discovery | Health endpoint / smoke test passes post-deploy |
| `toolchain-setup` | New repo, inconsistent lint/format, "set up eslint" | Languages? IDE (VS Code default)? Existing configs to preserve? | Skill scripts writing configs; `check.sh` as acceptance | CLI and IDE agree: `check.sh` passes AND .vscode settings map to the same tools; formatting failures surface as lint warnings |
| `deps-audit` | "Update deps", audit alerts, conflicts | Update everything or security-only? Breaking-change appetite? | `npm audit` / `dotnet list package --vulnerable`; summarising script | `check.sh` passes after updates; lockfile committed; conflict resolutions have documented rationale |
| `prereqs` | Tool missing, fresh machine, onboarding | OS? Package manager preference? | `check-prereqs.sh` (does 90% of the work) | Re-run `check-prereqs.sh` → all green |
| `essential-behaviours` | Project onboarding, "make sure X always happens" | Which behaviours (tests-after-change, aislop, format)? Which agent platforms in use? | `setup-hooks.sh`, `adapters/*/install.sh` | Hooks fire on a test commit; platform hooks confirmed in settings |
| `adr` | Architectural/infra decision point, "should we use X or Y" | Decision context? Options considered? Constraints? | `adr-new.sh` scaffolding `docs/ADRs/NNNN-*.md` | ADR exists, indexed in docs/index.md, states decision + consequences |

**Deliberate consolidations:**

- *"Running tests after each change"* is not a skill — it is exactly the thing small models forget. It becomes **enforcement**: `run-tests.sh` + git hooks + (optionally) a Claude Code PostToolUse hook, all installed by `essential-behaviours`.
- *"Consistency between typecheck/lint/format/build across CLI and IDE"* merges into `toolchain-setup`.
- *Local and remote deployment management* merge into `deploy` with a mode question.

## 4. Scripts inventory

**Language choice: bash, targeting bash 3.2** (the macOS floor), shellcheck-clean, zero dependencies. Works on mac/linux natively and on Windows via Git Bash (which every git user already has). Node is used only via inline `node -e` for JSON merging when node is present, with a printed manual fallback otherwise. This decision is itself documented in `guidance/languages/shell.md` as the worked example of "best shell choice".

| Script | What it does |
|---|---|
| `scripts/check.sh` | The quality gate. Detects project type (package.json / *.csproj / … via `lib/common.sh`), then runs: format check → lint → typecheck → build → unit tests → `npx aislop scan` (if available). Prints a short PASS/FAIL table with one fix-hint line per failure (e.g. `FAIL lint — run: npm run lint -- --fix`). Flags: `--fast` (staged files, skip build/tests), `--fix` (apply formatters/autofix first), `--suite <name>`. Exit 0 only on all-pass. Degrades gracefully: missing tool = SKIP with install hint, never a crash. |
| `scripts/run-tests.sh <suite>` | Dispatches to the project's `scripts/run-<suite>-tests.sh` if present, else falls back to npm scripts / `dotnet test` filters. `all` runs every discovered suite. |
| `scripts/check-prereqs.sh` | Checks required tools on PATH with version floors; prints per-OS install commands (brew/apt/winget) for anything missing. |
| `scripts/setup-hooks.sh` | Sets `core.hooksPath` to the hooks dir (or copies into `.git/hooks` on request); idempotent. |
| `scripts/hooks/pre-commit` | Runs `check.sh --fast`. Fast by design, so it never gets disabled out of frustration. |
| `scripts/hooks/pre-push` | Runs full `check.sh`. |
| `scripts/lint-docs.sh` | Enforces §2 on this repo itself: frontmatter present and well-formed, size budgets, index ⇄ description sync, no dead relative links. Runs in this repo's own CI. |
| `scripts/lib/common.sh` | Project-type detection, tool-presence checks, coloured PASS/FAIL/SKIP formatting. |
| `install.sh` (root) | Interactive installer — see §7. |
| `adapters/claude-code/install.sh` | Symlinks `skills/*` into `.claude/skills/`, merges `hooks.json` into `.claude/settings.json` (via `node -e`, manual fallback), copies `agents-files/remote/CLAUDE.md` if none exists. |
| `adapters/opencode/install.sh` | Appends/refreshes a marker-fenced "dev-environment skills" routing block in the project's AGENTS.md; optionally writes OpenCode command files. |

Skill-local scripts (e.g. `skills/adr/scripts/adr-new.sh`, testing-setup templates) live inside their skill directory.

## 5. Entry points and tiers

**`agents-files/local/AGENTS.md`** (small-context tier, ≤30 lines) — the whole contract on one screen:

- 5–6 non-negotiable rules inlined (intent comments, no `any`, zero warnings, small steps).
- "Before coding: read the ONE relevant file from `guidance/index.md` — never more than two docs at once."
- "After every change: run `scripts/check.sh` and fix what it reports. Do not summarise it away."
- "For multi-step tasks: find the matching skill in `skills/index.md` and follow its SKILL.md literally."
- "State the filename of any guidance doc you read." (Makes routing auditable by the user.)

**`agents-files/remote/AGENTS.md`** (capable-model tier, ≤30 lines) — same skeleton, plus: collaborate on plans before committing to approaches, follow references recursively, apply the judgment items in `guidance/process/after-coding.md` beyond what check.sh automates.

**`agents-files/remote/CLAUDE.md`** — the remote AGENTS.md content plus a short section: skills are installed at `.claude/skills`, hooks run check.sh automatically, don't duplicate that work.

The root `AGENTS.md` in this repo becomes a shim: "Pick your tier from `agents-files/` — if unsure, use `local`." Agents that auto-read AGENTS.md (OpenCode does) get routed correctly with zero platform-specific work.

## 6. Enforcement and activation per platform

Three layers, weakest to strongest; the strongest layer is platform-independent:

| Layer | Any agent (fallback) | Claude Code | OpenCode / others |
|---|---|---|---|
| **Routing** (right doc/skill at the right time) | AGENTS.md instructs: match the task against `guidance/index.md` and `skills/index.md` descriptions | Native skill activation via SKILL.md descriptions in `.claude/skills` | AGENTS.md routing block injected by the adapter; descriptions written as trigger phrases |
| **Behavioural** (remember to check/test) | AGENTS.md rule: "run check.sh after every change" | PostToolUse hook → `check.sh --fast` after edits; Stop hook prints an unfinished-gate reminder | AGENTS.md rule (some OpenCode setups support plugin hooks — investigate in phase 2, don't depend on it) |
| **Hard gate** (can't be forgotten) | **git pre-commit/pre-push hooks running check.sh** — works regardless of which model, editor, or human made the change | same | same |

## 7. Installer (`install.sh`)

Interactive, re-runnable, bash. Flow:

1. Confirm target repo path; detect existing AGENTS.md/CLAUDE.md, package.json, .csproj, git hooks.
2. Ask: install mode — **git submodule** (default; easy updates) or **copy** (vendored)?
3. Ask: agent tier(s) — local, remote, or both? Which platforms (Claude Code / OpenCode / other)?
4. Ask: languages/frameworks in use (pre-checked from detection) — used only to trim the routing block; all guidance is installed regardless, because lazy-loading makes unused docs free.
5. Copy chosen `agents-files/*` to the repo root — **merge, never clobber**: if AGENTS.md/CLAUDE.md exists, inject a marker-fenced block and tell the user to review.
6. Offer to run `setup-hooks.sh`; run the platform adapters chosen in step 3.
7. Print a "what was installed / what to do next" report ending with: run `scripts/check-prereqs.sh`, then `scripts/check.sh`.

## 9. Phasing and done-criteria

**Phase 1 — Restructure + core (one working session).**
Directory tree; migrate and improve the existing 13 docs into `guidance/` with frontmatter and budgets; write `standards/*` and `languages/*`; `check.sh` + `run-tests.sh` + `lib/common.sh` + `lint-docs.sh`; agents-files for both tiers; redirect stubs; new README.
*Done when:* `lint-docs.sh` passes on the whole repo; `check.sh` runs green against lcp-server (read-only, node path) and a toy dotnet project; the old `all-requests.md` entry instruction still resolves via stubs.

**Phase 2 — Skills + installer + enforcement (one to two working sessions; the time sink is testing install.sh merge behaviour in a scratch repo).**
All 11 skills; `install.sh`; hooks + `setup-hooks.sh` + `check-prereqs.sh`; both adapters.
*Done when:* installing into a scratch repo works end-to-end; a deliberately-bad commit is blocked by pre-commit with actionable output; Claude Code auto-activates `quality-review` and the PostToolUse hook fires; an OpenCode agent finds skills via the AGENTS.md block.

**Phase 3 — Breadth (one working session, incremental; can trail phase 4; the most token-heavy and most deferrable phase).**
`frameworks/*` (nestjs, express, aspnet-core, docker, docker-compose, improved react); `infra/*`; `ci/*`.
*Done when:* every doc is ≤60 lines, indexed, and names its verification tool (cfn-lint, tflint, actionlint, hadolint, …). Infra/CI docs are deliberately *thin decision guides + verification-tool pointers*, not encyclopedias — cloud specifics go stale fast, and the docs tell models to verify against current provider documentation (matching the existing "your training data could be outdated" rule). GCP/Azure/gitea are the lowest-value items in the brief: written last and short.

**Phase 4 — Validation with a small model (elapsed time watching external OpenCode runs, not agent usage; only the fixes it triggers come back here).**
Define 3 benchmark tasks on a scratch/sample project: a seeded bugfix, a small feature (new endpoint field + tests), and a docs update. Run each via OpenCode with a small-context model using `agents-files/local/AGENTS.md`.
*Done when:* all three tasks end with `check.sh` PASS and correct behaviour, without the operator reminding the model of any rule. Failures feed back into doc/script fixes. **This is the acceptance test for the whole project.**

Total: roughly 3–4 working sessions of agent usage — on a usage-limited plan, spread over a few days for limit reasons rather than effort reasons. Each phase leaves the repo in a usable state, and phase 1 alone delivers most of the practical benefit, so any phase boundary is a safe stopping point.

## 10. Decisions and defaults

Confirmed with the user:

- **Portable core + adapters** — skills are plain playbooks + scripts; Claude Code and OpenCode wiring is generated from them.
- **OKF-lite** — frontmatter (type/title/description/tags) + index.md per directory + cross-links; no timestamp field (git owns history).
- **Core first, breadth phased** — full treatment for the stack in real use (TS/C#/shell, NestJS/React/Express, Docker, AWS, GitHub Actions); GCP/Azure/Terraform/GitLab/gitea later and thin.
- **Submodule + installer** — the submodule stays the source of truth; `install.sh` wires entry files, skills, and hooks.

Defaults adopted (change any of these before the relevant phase if desired):

- **aislop/ponytail are optional in the gate** — check.sh reports SKIP with an install hint when they're absent; external tools never break the gate.
- **Windows floor is Git Bash** — no PowerShell twins until a real Windows consumer appears (YAGNI).
- **Redirect stubs** (`all-requests.md`, root `AGENTS.md`) are deleted once the lcp-server migration is confirmed.
- **`guidance-overrides.md` convention** — consumer repos document deliberate exceptions to standards there, so deviations are visible rather than silent.
- **lcp-server `no-explicit-any`** — recommendation is to enable the rule, decided together during the deferred migration (§8).
