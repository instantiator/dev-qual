# Plan: usage review improvements

Requested by `prompts/002.1 - usage review improvements.md`. **First implementation step: copy this plan to `prompts/002.2 - usage improvement plan.md`.**

## Context

The repository currently ships guidance, skills, and scripts that get an agent to *write* code well. Eight gaps surfaced in real use:

1. Work that finishes with follow-ups loses them — there is no convention for recording deferred items or their trigger conditions.
2. Sub-agent model choice is unaddressed, so capable-but-expensive models do mechanical work.
3. Named quality frameworks (SOLID, YAGNI, KISS, 4Cs) are encoded only implicitly, so an agent can't self-check against them.
4. Database atomicity is not mentioned anywhere.
5. `check.sh` covers node and dotnet only; Python has no path, and `markdownlint` is mandated by guidance but never actually run by the gate.
6. The gate has fast and full modes but no *comprehensive* mode (all suites + security audit), and no unit-of-work cadence tells an agent when to run which.
7. `pre-commit` runs checks but has no place for the auto-modifying steps (formatting, generated files, licence lists) that must land inside the same commit.
8. A project installed months ago has no way to find out what has changed upstream.

Outcome: the same terse, script-backed system, extended to close all eight — without breaking `install.sh`, the `CLAUDE.md`/`AGENTS.md` dual support, or per-platform skill installation.

### Decisions taken

| Decision | Choice |
|-|-|
| Language coverage | Python (ruff + mypy + pytest). Plus `markdownlint` wired into the gate — [markdown.md](guidance/languages/markdown.md) already mandates it, so the gate not running it is an inconsistency, not new scope. |
| Deferred work | `docs/outstanding-issues.md` is the single source of truth. Platform memory is a mirror, never relied on. |
| Upgrade | Drift report (`scripts/check-install.sh`) + thin `update-latest` skill that re-runs `install.sh`. No three-way merge. |
| Model naming | Capability tiers described; actual models discovered at runtime and confirmed with the user once. No hardcoded model table. |

### Standing constraints

- **Line budgets are enforced** by [lint-docs.sh](scripts/lint-docs.sh): index 40, standard 60, process 80, skill 100, entry files 30 (hard). Entry files sit at 24–25 lines, so they get **one line each at most**.
- **Every mandated step must have a free path.** Sub-agents, paid model tiers, and platform memory are all optional accelerators; the local tier must stay fully functional without them.
- **A doc's `description` is duplicated verbatim in its index** — `lint-docs.sh` fails otherwise.

## 1. Outstanding and deferred work

**New:** `guidance/process/outstanding-work.md` (type `process`, ≤80 lines)

- Convention: `docs/outstanding-issues.md`, listed in `docs/index.md`.
- Entry format — one table row: what, why deferred, **measurable condition**, where the related code lives.
- Condition rule: "return to this" is invalid. A condition must be checkable without judgement — a version number, a date, a file existing, a test passing, a dependency reaching a release. This extends the existing unconditioned-`TODO` rule in [pitfalls.md](guidance/standards/pitfalls.md), which should gain a cross-link.
- **Conditional review procedure** (run after the last unit of work): read the doc → evaluate each condition → trivial + met = do it and tell the user → non-trivial + met = present a table and ask which to include.
- Mirror to platform memory where one exists (Claude Code), stating the same measurable condition; never depend on it.

**Changed:**

- [after-coding.md](guidance/process/after-coding.md) — new "4. Outstanding work" section: record anything left undone, then route to the new doc. (28 → ~35 lines, budget 80.)
- [pitfalls.md](guidance/standards/pitfalls.md) — the `TODO`/`LATER` bullet links to `outstanding-work.md`.
- [process/index.md](guidance/process/index.md) — new entry.
- Both entry files — one line: unfinished work goes in `docs/outstanding-issues.md` with its condition.

## 2. Model allocation

**New:** `guidance/process/model-allocation.md` (type `process`, ≤80 lines)

Structured so the escape hatch comes **first** — a single model with no sub-agents reads three lines and stops:

1. **Short-circuit** — no sub-agent support, or only one model available? Skip this doc. Do the work.
2. **Tiers, not names** — high-reasoning (architecture, ambiguous problems, plan authoring), mid (normal implementation), fast/cheap (mechanical edits, renames, applying a stated decision across files).
3. **Discovery** — if the preferred set is unknown, enumerate the models this provider actually offers, order by capability and token cost, note which is efficient and which handles complexity, present to the user, and record the answer in `docs/agent-models.md` (indexed in `docs/index.md`). Ask once, not per task.
4. **On receiving a prompt** — if the task suits a different tier than the current model: either HALT and recommend the switch, or delegate to a sub-agent at the right tier.
5. **In planning mode** — produce a task→model table. Where a task could suit a cheaper model *if it were more specific*, add the specificity (concrete steps, exact file lists, exact changes) rather than escalating the model.
6. **In build mode** — identify tasks → evaluate available models → delegate downward wherever a cheaper model suffices.
7. **Split decision from mechanics** — the capable model makes the judgement call, the cheap model applies it across files.

**Changed:** [before-coding.md](guidance/process/before-coding.md) gains one line routing to it; `process/index.md` gains an entry. Deliberately **not** added to `agents-files/local/AGENTS.md` — small-context agents can't act on it, and the line costs budget.

## 3. Quality principles

**New:** `guidance/standards/principles.md` (type `standard`, ≤60 lines)

One doc, not five. Each framework gets a line or two that maps it to the concrete rules already in this repo, plus where it does and doesn't apply:

- **YAGNI / KISS** — already the spine of [common.md](guidance/standards/common.md) and [readability.md](guidance/standards/readability.md); named here so an agent can cite them.
- **SOLID** — full force in OO code (C#, NestJS). Reduced form elsewhere, stated per paradigm: single-responsibility applies to any function, module, or script; dependency-inversion becomes "take collaborators as parameters" in functional TS and "take paths and flags as arguments, don't hardcode" in shell; interface-segregation becomes "don't force a caller to supply what it doesn't use". Explicitly note that Liskov and open/closed are largely inert in procedural Python and shell — don't force them.
- **Readability, Maintainability, Efficiency, Reliability, Security** — the review lens.
- **Correctness, Clarity, Completeness, Consistency** — the acceptance lens for a unit of work.

Framed as *two checklists* (before a unit of work: does the plan violate YAGNI/KISS/SRP? after: 4Cs) rather than an essay — the existing docs stay the detail.

**Changed:** [quality-review](skills/quality-review/SKILL.md) gains a step reviewing against these; `standards/index.md` gains an entry. Language docs are **not** each given a principles section — routing avoids duplicating budget-constrained content.

## 4. Database guidance

**New:** `guidance/standards/databases.md` (type `standard`, ≤60 lines)

- **Atomicity** — changes that must succeed or fail together go in one transaction; name the unit of work the transaction represents. No partial writes left behind on error.
- Don't hold a transaction open across network calls, user interaction, or long computation.
- Migrations are versioned, forward-only by default, and reviewed before applying (routes to [infra/verification.md](guidance/infra/verification.md)).
- Parameterised queries only — never string-concatenated SQL. (Non-negotiable; security.)
- Test the rollback path, not just the happy path.

No new skill — the rules are short and belong with the standards.

## 5. Python and linter coverage

**New:** `guidance/languages/python.md` (type `standard`, ≤60 lines) — ruff (lint + format, one tool replacing black/flake8/isort), mypy (typecheck, strict where the project allows), pytest, `pip-audit` for vulnerabilities, type hints on public functions, docstring conventions matching [common.md](guidance/standards/common.md)'s intent-comment rule.

**Changed — [scripts/lib/common.sh](scripts/lib/common.sh):**

- New `detect_stacks` returning a newline-separated list (node / dotnet / python), so a polyglot repo is checked properly. `detect_project_type` becomes its first line, keeping `check-prereqs.sh` and `run-tests.sh` working unchanged.
- Python markers: `pyproject.toml`, `setup.py`, `requirements.txt`.

**Changed — [scripts/check.sh](scripts/check.sh):**

- Loop over `detect_stacks` instead of the current single `if/elif` on `TYPE`.
- Python stages: `ruff format --check` → `ruff check` → `mypy` → `pytest`. Missing tools SKIP with an install hint, matching the existing pattern.
- Markdown stage: `markdownlint` when `.md` files exist, alongside the existing generic `shellcheck` stage.
- **Fix:** aislop currently runs only when `TYPE = node`, though it supports 8 languages. Gate it on `npx` availability, not stack.

**Changed — [scripts/check-prereqs.sh](scripts/check-prereqs.sh):**

- Python tools per detected stack; `markdownlint` when markdown is present.
- New `--install` flag: run the printed install command for the detected OS instead of only reporting. This is the "check-and-install" ask — a flag on the script that already does 90% of the work, not a new skill.

**Changed — [skills/prereqs/SKILL.md](skills/prereqs/SKILL.md):** document `--install` and the per-language linter set.

`hadolint` and `actionlint` are already checked by `check-prereqs.sh` but not run by the gate. Left out of scope here and **recorded as the first entries in this repo's own `docs/outstanding-issues.md`** — dogfooding §1.

## 6. Quality gates and units of work

**Changed — [testing-loop.md](guidance/process/testing-loop.md)** (24 → ~50 lines, budget 80) gains the unit-of-work cadence:

- Split coding work into units that can be evaluated independently.
- **Before each unit:** check the plan against `principles.md`; decide what tests the unit needs (unit always; heavier tiers where warranted).
- **After each unit:** `check.sh --fast`. Any change made in response is re-checked.
- **After the last unit:** `check.sh --comprehensive`, re-check after fixes, update docs, run the conditional-outstanding-task review.

**Changed — [scripts/check.sh](scripts/check.sh):** new `--comprehensive` flag = full gate + `run-tests.sh all` + package security audit (`npm audit --audit-level=high` / `dotnet list package --vulnerable` / `pip-audit`, each SKIP-if-absent). Existing `--fast` and default behaviour unchanged, so the hooks and the Claude post-edit hook keep working as-is.

**Changed:** [after-coding.md](guidance/process/after-coding.md) and [quality-review](skills/quality-review/SKILL.md) reference the three modes explicitly. README's "quality gate" section documents all three.

## 7. pre-commit ordering

**Changed — [scripts/hooks/pre-commit](scripts/hooks/pre-commit):**

1. Run `check.sh --fast`; abort on failure (unchanged).
2. If `scripts/pre-commit-fixups.sh` exists in the project, run it — the extension point for formatting, generated files, and licence-list regeneration. This repo ships no generators; each project owns its own.
3. Re-stage **only files that were already staged**, captured via `git diff --name-only --cached` before step 2.

**Safety detail that must not be skipped:** a file staged with `git add -p` has unstaged hunks. Re-adding it wholesale would silently commit work the user deliberately held back. Detect those files (staged *and* dirty in the worktree), leave them unstaged, and print a warning naming them.

`pre-push` keeps running the full gate — comprehensive is agent-invoked at end-of-work, not push-time, because a browser suite on every push is how hooks get disabled.

## 8. Update to latest

**New — `scripts/check-install.sh`:** reports drift between the submodule and what is installed in the target project:

- `CLAUDE.md` — copied once, never refreshed → real drift.
- Git hooks installed with `--copy` → real drift (`core.hooksPath` installs can't drift).
- `.claude/settings.json` hook entry — present / absent / modified.
- The `AGENTS.md` dev-environment block — compares against the current tier file.
- Skills: `.claude/skills/*` symlinks are always current; **flags any that are real directories** (copied, or a stale link), which is the only way they drift.

Output is a PASS/DRIFT/MISSING table via the existing `record_result`/`report_results` helpers in [common.sh](scripts/lib/common.sh) — no new reporting code.

**New — `skills/update-latest/SKILL.md`:** `git submodule update --remote` → run `check-install.sh` → show each difference to the user with what upstream changed and why → re-run `install.sh` for the mechanical parts → hand-merge anything the user has customised, preserving their edits.

**Bootstrap for a project that doesn't have the skill yet:** `git submodule update --remote dev-environment && ./dev-environment/install.sh` already does it — `install.sh` is idempotent, marker-based, and installs the new skill on the way through. Documented as a one-liner in the README rather than built as new machinery.

## 9. Cross-cutting updates

- **Indexes:** `guidance/standards/index.md` (+2), `guidance/process/index.md` (+2), `guidance/languages/index.md` (+1), `skills/index.md` (+1) — all well inside the 40-line budget. Descriptions must match the docs verbatim.
- **Entry files** (30-line hard budget, currently 24–25): `local/AGENTS.md` +1 line (outstanding work). `remote/AGENTS.md` +2 lines (outstanding work, model allocation). `remote/CLAUDE.md` +1 line (mirror deferred items to memory, file still governs). If any file exceeds 30, raise the entry budget to 32 in [lint-docs.sh](scripts/lint-docs.sh) — a one-number change — rather than cutting existing rules.
- **README:** Python in the gate description, the three gate modes, the update-latest bootstrap one-liner, and ruff/markdownlint added to the third-party tools table.
- **`install.sh`:** unchanged structurally. Its "Next steps" report gains a `check-install.sh` line.

## Sub-agent allocation (dogfooding §2)

Presented as the guidance requires; whether to actually delegate is yours to decide at execution time.

| # | Task | Tier | Why |
|-|-|-|-|
| 1 | Write `principles.md`, `model-allocation.md`, `outstanding-work.md` | High-reasoning | Judgement-heavy: deciding which SOLID facets survive in non-OO code, and how terse the escape hatch can be while still working. |
| 2 | Write `databases.md`, `python.md` | Mid | Well-understood content, fixed format, existing docs as templates. |
| 3 | `check.sh` + `common.sh` stack refactor | Mid | Real logic, bash 3.2 constraint, must not regress node/dotnet. |
| 4 | `check-prereqs.sh --install`, `check-install.sh` | Mid | Mechanical once the table of what-to-check is fixed by task 3. |
| 5 | `pre-commit` fixup + safe re-stage | High-reasoning | The partial-staging edge case is where this goes wrong; small diff, high blast radius. |
| 6 | Index entries, entry-file lines, README, cross-links | Fast/cheap | Fully specified by §9 — exact files, exact line counts, descriptions copied verbatim. |
| 7 | `update-latest/SKILL.md` | Mid | Follows the established SKILL.md shape once §8's drift list is fixed. |

Tasks 1, 3, and 5 are the decisions; 2, 4, 6, 7 are mechanical once they land — so the split-decision-from-mechanics rule applies literally here.
