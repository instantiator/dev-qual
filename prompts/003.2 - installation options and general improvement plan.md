# Plan: installation options and general improvements

Requested by `prompts/003.1 - installation options and general improvements.md`.

**Status: done.** Deviations from the plan as written:

- Stage 8c (C# tools) was deferred, then built in the same round once the .NET SDK was installed.
- pi's published release (0.73.1) lacks events described in its docs on `main` (e.g. `agent_before_settle`), so the extension follows the shipped types: the stop gate uses `agent_end` and `sendMessage(triggerTurn)`.
- Added at the user's request: user-scope installs offer git hooks per repository at session start (a decline is remembered in the repo's git config).
- Added at the user's request: the pre-commit hook gates the staged snapshot (an export of the index), not the working tree, after unstaged work blocked unrelated commits twice during this plan.
- CI (`test-tools`) runs on pull requests, so the work went up as a draft PR. Its first run caught an SC2015 that the runner's shellcheck 0.9.0 reports and local 0.11.0 does not.
- Found and fixed along the way: the old post-edit hook exited 1, so Claude never saw its failures; `setup-hooks.sh --copy` installed into the wrong repo when run from elsewhere; the gate linted a nested dev-qual checkout as if it were the project's code; vulnerability reports could print a false all-clear (no npm lockfile, unrestored .NET project); `dotnet run <file>.cs` ran the cwd's project instead of the tool; the C# baseline was invalid XML and its test-project exemption never applied.

- **Branch:** `003/installation-and-general` (already created by the user; work on it directly)
- **Commits:** one per stage, made only after that stage's gate passes (agreed with the user)
- **Orchestrator:** high-reasoning model (Opus). Sub-agent tiers follow `guidance/process/model-allocation.md`: **Mid** = Sonnet, **Fast** = Haiku.

## Context

dev-qual can only be installed as a git submodule inside a repo. It records nothing about the install choices, so upgrading means re-answering questions and there is no clean way to switch it off. Planning, which the prompt says dev-qual should govern, is covered by one sentence in `before-coding.md`. No script tests itself. Language guidance is a flat set of files with nowhere to put per-language tools.

Outcome: dev-qual can be installed per repo or per user, upgraded, and enabled or disabled with one command. It can be packaged for pi. It governs planning through a skill. It ships tested, per-language helper tools, and deterministic agent hooks enforce what memory can't.

### Decisions taken (with the user)

| Decision | Choice |
|-|-|
| Installer | Keep `install.sh`. The README's "How to use" text is corrected to `./dev-qual/install.sh`. |
| Git hooks at user scope | Opt-in per repo (`setup-hooks.sh`). Global git config is never touched. |
| Disable | Unwire everything (blocks, symlinks, agent hooks, hooksPath) but keep the recorded choices, so `enable` restores the setup exactly. |
| Tools this round | Baseline lint configs, a vulnerability report that ranks next actions, and a stale-docs detector. The move-method tool is deferred to `docs/outstanding-issues.md`. |
| Agent hooks | A session-start update check and a Stop-time gate. The Stop gate runs only when uncommitted non-docs files have changed. There is no `--no-verify` blocker. |

### Standing constraints

- `scripts/lint-docs.sh` line budgets: index 40, standard 60, process 80, skill 100. Entry files have a hard limit of 30 lines and are currently about 25, so each gets **at most +3 lines**. Each doc's `description` must appear verbatim in its index.
- Shell is bash 3.2 compatible and shellcheck-clean (`guidance/languages/shell.md`). JSON handling uses node, as `adapters/claude-code/install.sh` already does.
- Reuse: `merge_block` (`install.sh:57`), `record_result`/`report_results`/`detect_stacks` (`scripts/lib/common.sh`), `block_between` (`scripts/check-install.sh:33`), and the per-suite convention in `scripts/run-tests.sh`.

### Answers to the prompt's open questions

- **Does dev-qual use agent hooks?** One: a Claude Code `PostToolUse` hook that runs `check.sh --fast` after `Edit|Write` (`adapters/claude-code/hooks.json`). Git hooks handle commit and push. This plan adds session-start and Stop hooks through a single dispatcher.
- **What else is missing from the guidance?** There is no security standard (currently a few bullets in `before-coding.md`) and no error-handling or logging standard. Stage 9 adds both. Other gaps, such as API design and accessibility, go to outstanding-issues with conditions.
- **Relieving agents of effort:** baseline lint configs turn written rules into lint errors. The vulnerability report and stale-docs detector replace manual procedure. Stage 8 also checks whether `aislop` has an autofix mode; if it does, `check.sh --fix` runs it.

## Stage 3: Install scopes and recorded state (Mid; orchestrator reviews the design)

- `install.sh` gains `--user` (default scope: `--project`) and `--from-config`. It writes the chosen options to a state file:
  - repo scope: `<project>/.dev-qual.env`
  - user scope: `${XDG_CONFIG_HOME:-~/.config}/dev-qual/config.env`
  - Keys: `SCOPE TIER PLATFORMS HOOKS CHECKOUT ENABLED` as shell `KEY=value`, read by sourcing.
- Move `merge_block` and `block_between` into `scripts/lib/common.sh`, gaining a `remove_block <file> <marker>` counterpart. Adapters and `check-install.sh` reuse them.
- **Path resolution:** when merging an entry file, the installer replaces its first `dev-qual/`-locating line (line 3 of every tier file) with a scope-specific line. At repo scope it says `dev-qual/` is in this repo. At user scope it says "dev-qual is installed at `<abs checkout>`; read every `dev-qual/` path in its docs as that path". No other doc is rewritten. `check-install.sh` applies the same substitution before comparing.
- **Targets by scope:**

  | Platform | Repo scope | User scope |
  |-|-|-|
  | Entry block | `<project>/AGENTS.md` | `~/.config/opencode/AGENTS.md`, `~/.claude/CLAUDE.md` |
  | Claude skills | `<project>/.claude/skills/` symlinks | `~/.claude/skills/` symlinks |
  | Claude hooks | `<project>/.claude/settings.json` | `~/.claude/settings.json` |
  | Git hooks | `setup-hooks.sh` (unchanged) | not installed (per-repo opt-in) |

  Verify the OpenCode user config path against current OpenCode docs before relying on it.
- `CLAUDE.md` becomes a marker block through `merge_block`, instead of a copy-if-absent. Migration: an unmarked `CLAUDE.md` identical to the template is replaced by the block; anything else gets the block appended with a NOTE, as `AGENTS.md` does today.
- `scripts/agent-hook.sh <event>` is the single dispatcher for agent hooks. It exits 0 silently if the state file says `ENABLED=0`. In this stage it handles only `post-edit`, which runs `check.sh --fast`. The Claude adapter **generates** its hooks JSON with the absolute dispatcher path for the chosen scope, replacing the static `adapters/claude-code/hooks.json`. The node merge dedupes on the command string containing `agent-hook.sh`.
- Guard against double wiring: if a user-scope install exists and the project also has a repo-scope install, the repo scope wins. `agent-hook.sh` at user scope exits if `<cwd>/.dev-qual.env` exists.

**Tests** (`scripts/tests/test_install.sh`, using a temp `HOME` and a temp git repo): check both scopes, re-running (idempotent, with no duplicate blocks or hook entries), `--from-config` reproducing the same result, CLAUDE.md migration, and `check-install.sh` passing straight after install at each scope.
**Gate:** `check.sh --fast` and `run-unit-tests.sh`. **Commit.**

## Stage 4: Upgrade, update check, and enable/disable (Mid)

- Each adapter gains `--remove`, which undoes exactly what it installs: remove the marker blocks, the symlinks that point into the checkout, and the settings.json entries containing `agent-hook.sh`.
- `scripts/toggle.sh enable|disable|status [--user | --project <dir>]`:
  - **disable** runs every adapter with `--remove` for the recorded platforms. It unsets `core.hooksPath` if that points at this checkout, and removes copied hooks only if they are byte-identical to ours; otherwise it warns. Then it sets `ENABLED=0`.
  - **enable** runs `install.sh --from-config` and sets `ENABLED=1`.
  - **status** reads the state file and runs `check-install.sh`.
- `scripts/check-updates.sh [--quiet]` never blocks. It compares `HEAD` against the already-fetched `origin/HEAD` (falling back to `origin/main`) and prints "dev-qual is N commits behind — offer `dev-qual/scripts/upgrade.sh`". If the last fetch is more than a day old (timestamp in `${XDG_CACHE_HOME:-~/.cache}/dev-qual/`), it starts a background `git fetch`. Offline, it stays silent.
- `scripts/upgrade.sh [--user | --project <dir>]`:
  - repo scope: `git -C <project> submodule update --remote <checkout-relpath>`
  - user scope: `git -C <checkout> pull --ff-only`
  - Then it **execs the updated** `install.sh --from-config`, and finally runs `check-install.sh`.
- `agent-hook.sh session-start` runs `check-updates.sh --quiet` and prints the result to the transcript. Wire it as a Claude `SessionStart` hook.
- Entry files: add one line: "Before starting work, run `dev-qual/scripts/check-updates.sh`; if it reports updates, offer to run `dev-qual/scripts/upgrade.sh` first."

**Tests:** in `test_toggle.sh`, a disable/enable round-trip restores an identical tree at both scopes. `test_upgrade.sh` uses a local bare remote with a new commit, which upgrade picks up, then re-installs. `test_check_updates.sh` covers behind, level, and no remote.
**Gate:** `check.sh --fast` and `run-unit-tests.sh`. **Commit.**

## Stage 5: Stop-time gate and plan tracking (Mid)

- `scripts/plan-status.sh [--project <dir>]` lists unchecked `- [ ]` stage lines in `docs/plans/*.md` whose frontmatter has `status: active`.
- `agent-hook.sh stop`:
  1. Read the hook's stdin JSON. If `stop_hook_active` is true, exit 0, so it blocks at most once. Use grep, not jq.
  2. "Code changed" means `git status --porcelain` lists a path that is not `*.md` and not under `docs/`. If none, exit 0: no gate for docs-only tweaks.
  3. Run `check.sh --fast` and `plan-status.sh`. If either reports something, print it to stderr and exit 2, which blocks the stop and feeds the output to the agent.
- Wire it as a Claude `Stop` hook through the generated hooks JSON.

**Tests** (`test_agent_hook.sh`): check docs-only changes (no gate), a code change with a failing lint (blocked), `stop_hook_active` (allowed through), and an active plan with unticked stages (blocked, listing the stages).
**Gate:** `check.sh --fast` and `run-unit-tests.sh`. **Commit.**
