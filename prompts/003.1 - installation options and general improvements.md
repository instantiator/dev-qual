## Additional documentation

Please add a note in README about the expected way of working - eg. a section entitled "## How to use dev-qual", eg. with text like this:

> Use the setup wizard to install dev-qual: `./scripts/setup-wizard.sh`
> 
> dev-qual is geared for a planning/implementation cycle. Switch your agent into planning mode, and describe the plan you want it to create. Let your most capable agent model drive this planning step, so that it can make the best assessments, and do a lot of the work upfront. It will prepare a plan that divides the work amongst sub-agents for token-efficiency (where other models are available). Implementation of that plan will be orchestrated by your most capable agent - handing off tasks to less capable agents, reviewing their work and resolving complex issues.
>
> It will ensure:
> - High quality code, using the guidance in dev-qual
> - Tests are written at appropriate levels (unit, integration, end-to-end)
> - A plan that's broken into steps, each gated on a quality check
> - Project documentation kept up to date
>
> dev-qual also installs commit hooks (fast quality tests) and push hooks (full quality tests) to help catch issues before they enter your code base.

## Explicit planning input

Preparing a plan for a piece of work is something that should be governed by dev-qual. At the moment, that's not present, so please add some guidance/skill that pulls together the things already known (eg. notes in `before-coding.md`) and includes:

- plans should be broken into individual stages
- each stage should have an assigned model or sub-agent if the current environment allows (see `model-allocation.md`)
- emphasise the importance of providing enough information to a less capable agent to help it get its task right first time (because failing, retrying, and/or checking with the orchestrating agent will be more expensive than giving it more detail)
- each stage should include writing of tests for new changes
- each stage should end with a quality gate that runs the fast tests + any new (longer) tests
- plans should always end with a step which updates existing documentation that should change as a result of the work

Wherever possible, refer out to existing documentation, skills, scripts, or guidelines.

New plans should state the branch they're expected to work on, and should (by agreement with the user) determine if each stage in the plan should create a separate commit once passed, or if the whole plan should create a single commit, or if not to commit at all.

## Relieving agents of effort

Are there opportunities to add scripts that will support the rules and tools?

ie. If there are specific fixes that are likely to come up frequently, can they be written as a script that will check some things and make those fixes?

ie. Can we write additional linting rules to help detect and/or fix code so that it meets requirements in the guidelines for the various languages?

eg. Could we write a tool to help detect and refactor a method from one class into another? (For a language where that makes sense.) (It would need to create the new class file if not present, and not clobber anything already in the class it's writing to.) If not, could we write a linting tool that generates a recommendation to do it with specifics in the resulting error/warning so that it's easier for the agent to know what's required? (Perhaps `aislop` already does this.)

eg. Could we write a tool that checks all dependencies for vulns and prepares a list of recommended steps? (Or attempts them?)

It probably makes sense to associate these new tools with specific language guidance. That way, the choice of language to implement them in can favour the language that the guidance is about (so ensuring that the language is definitely already installed). These scripts will likely need to be installed alongside the skills that would apply them.

- `guidance/languages/cli-tools/`
- `guidance/languages/csharp/`
- etc.

Keep `guidance/languages/index.md` but update this (and all other references to language guidance across dev-qual) to ensure the language guidance is found and used correctly.

Write tests for the new tools, and ensure these are run as a part of a CI process, and as a pre-push hook in this repository. (Create a github workflow called "test-tools" that runs against each PR, whenver a merge is made to `main`, and can be manually triggered in the GitHub Actions UI.)

Ensure these new tools are installed correctly alongside their skills, and ensure they are written into the skills and processes so they're expected by plans, and fully used when plans are implemented.
