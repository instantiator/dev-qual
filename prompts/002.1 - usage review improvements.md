## Outstanding tasks

To ensure that when work completes with notes or outstanding follow-up tasks, those are not lost:

- Outstanding issues should be noted in an appropriately named (and easy to find) document (eg. `outstanding-issues.md`) as well as shared with the user in a final summary of the work completed
- Work that has been deferred until conditions are met (or time has passed) should also be stored in a memory that explicitly states measurable conditions upfront (not just 'return to this') to ensure it's addressable when the conditions are met

## Model allocation

When working with a provider and coding assistant that can utilise sub-agents to complete tasks as a part of a plan or as part of a regular piece of work, it's good to reduce token usage by making an efficient choice of model for each task.

When responding to a user prompt, if the high-level task is appropriate for a different model than the current (eg. it should be completed by Claude Opus, but the current model is Sonnet, or eg. the current model is Opus but that would be unnecessarily expensive) either:

- HALT and recommend a switch of model
- employ a sub-agent with the appropriate model to complete the task

If the subset of preferred models to choose between is not known (eg. when using opencode which offers a variety of models from different providers, and the user has not yet been asked) first check with the user:

- Offer a list of available models that you're aware of
- Order the list by capability and token consumption - noting which are more token efficient, and which are best placed to solve complex tasks
- Record a memory of the models the user wishes to include in the set of available models for selection

In some cases, models other than the current, are not available or not appropriate. If that's the case, a lot of this change can be short-circuited, and so the guidance and skills should offer a quick "don't think about it" path to keeping thoughts about the decision making small.

Where possible, in planning mode:

- Prepare a table of tasks that can be handed to sub-agents, indicating which model will be assigned to complete each.
- Where the task could be modified to support a less capable sub-agent, give it additional detail (ie. provide concrete steps, or specific lists of files, or specific changes)
- If a task requires a decision that's appropriate for the current / more capable model, but will likely be followed by mechanical steps, make the decision with the more capable model, and then assign the mechanical steps to the less capable model as a sub-agent

Where possible, in build mode:

- Identify the tasks
- Before initiating them: Evaluate the available models for sub-agents
- Where a smaller, less capable, model could complete the task, use it for the sub-agent
- Where the task could be modified to support a less capable sub-agent, give it additional detail (ie. provide concrete steps, or specific lists of files, or specific changes)
- If a task requires a decision that's appropriate for the current / more capable model, but will likely be followed by mechanical steps, make the decision with the more capable model, and then assign the mechanical steps to the less capable model as a sub-agent

## Formalised code quality frameworks

There are a number of code quality frameworks worth incorporating into the guidance:

- SOLID
- YAGNI
- KISS
- Readability, Maintainability, Efficiency, Reliability, Security
- Correctness, Clarity, Completeness, Consistency

Some are already encoded, so please check what's already considered. Some of these overlap (quite a lot!) so that should help to reduce the volume of changes. Each of these may apply _to varying degrees_ to different languages, eg. SOLID is perhaps better for object oriented coding, but some aspects of SOLID guidance can still apply to code that's not very OOP-like (eg. working with python when the code is arranged more like a script; or working with typescript/js when the code is functional but not so object oriented). Sift out good guidelines for each supported language and for shell scripts, and include in the skills and guidance.

## Quality gates

Please review and ensure that the current guidelines and skills ensure that the guidelines and skills are aligned with this:

**Before each unit of work:**

- Coding work should be split into distinct units of work that can evaluated independently
- Each unit of work should be evaluated before starting for alignment with the code quality framework guidelines in use
  - eg. whichever rules have been derived from SOLID, YAGNI, KISS, etc.
- Each unit of work should include writing/modifying unit tests for new and changed code
  - It may also include writing more complex tests (eg. integration tests, browser tests, etc.)

**After each unit of work:**

- A fast-check quality gate should run after each unit of work
- Changes made after each quality gate check should be re-checked

**After the last unit of work:**

- A comprehensive-check quality gate should run
- Changes made after each quality gate check should be re-checked
- Documentation relevant to the changes made should be updated or created
- Conditional outstanding tasks should be reviewed

**Fast-checks:**

- Compiler (0 errors, 0 warnings)
- Linter (0 errors, 0 warnings)
- Unit tests (0 errors)
- Fast code quality checks (eg. aislop)
- Other fast test suites (eg. those that do not require lengthy containerisation or browser interactions) (0 errors)

**Comprehensive-checks:**

- All fast-checks
- All outstanding test suites
- Code quality checks (eg. this is an opportunity to raise issues around separation of concerns)
- Package security audit (0 severe / high importance issues, 0 other issues that can be mitigated)

**Conditional outstanding tasks:**

- Check memory and the outstanding tasks doc (if it exists) for all conditional outstanding tasks
- Check each for its conditions
- If its conditions are met, and the task is trivial, inform the user and complete the task
- For all outstanding tasks where the conditions are met, but the task is not trivial, compile a table offering to complete these tasks and ask the user which to include in the current work

### Git hooks

The order of actions in `pre-commit` and `pre-push` hooks are important, and may need reviewing.

**pre-commit:**

1. Run the fast checks to confirm that the code is in an acceptable state
2. Run any steps that automatically modify files, and then incorporate these changes into the commit
   - any other automated documentation / generated files
   - licensing list re-generation
   - formatting (eg. prettify)
